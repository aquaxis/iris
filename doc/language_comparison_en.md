# Comparing IRIS, SystemVerilog and Veryl

## What this document covers

Three hardware description languages set side by side, compared on syntax, on
how much has to be written, and on simulation speed. Which one comes out ahead
depends on the design, so every figure carries the conditions it was measured
under.

All the figures are regenerated by `example/comparison/run.sh`. Run it before
quoting them.

The three:

**SystemVerilog**: the language standardised as IEEE 1800. EDA tools accept it
directly.

**Veryl**: a language that compiles to SystemVerilog, so the existing tools keep
working while the syntax is modern.

**IRIS**: a language that compiles to SystemVerilog and also has a simulator of
its own.

Veryl and IRIS are solving the same problem. Both discard SystemVerilog's syntax
without discarding its ecosystem.

## Syntax

| Feature | SystemVerilog | Veryl | IRIS |
|---|---|---|---|
| Blocks | `begin ... end` | `{ ... }` | `{ ... }` |
| Declaration (combinational) | `wire [7:0] data` | `let data: logic<8>` | `let data: bit[8];` |
| Declaration (sequential) | `reg [7:0] data` | `var data: logic<8>` | `var data: bit[8];` |
| Branching | `case ... endcase` | `case { ... }` | `match { ... }` |
| Combinational logic | `assign` / `always_comb` | `assign` / `always_comb { }` | `let` / `comb { }` |
| Sequential logic | `always_ff @(posedge clk)` | `always_ff (clk) { }` | `sync(clk.posedge) { }` |
| Modules | `module ... endmodule` | `module ... { }` | `mod ... { }` |
| Assignment | `=` (blocking) / `<=` (non-blocking) | `=` (one form) | `=` (one form) |
| Reserved words | about 220 | 85 | 58 |
| Grammar rules | not counted | 199 | 209 |

IRIS's reserved words come from specification §2.4, Veryl's from the grammar
file `tools/veryl.ebnf` was derived from. The rule counts are those of
`tools/iris.ebnf` and `tools/veryl.ebnf`. SystemVerilog's figure of about 220 is
carried from the specification; neither it nor SystemVerilog's rule count was
recounted here.

Veryl and IRIS move away from SystemVerilog in much the same direction. Both use
braces, collapse the two assignment operators into one, and cut the reserved
words to under a third.

## How much has to be written

Only designs verified to behave identically are compared. Counting lines across
circuits that do different things says nothing.

The IRIS and Veryl versions are handwritten; the SystemVerilog is what `iris2sv`
generates.

The ALU, covering RV32I's ten operations:

| | Code lines | Non-space characters | Longest line |
|---|---|---|---|
| IRIS (handwritten) | 30 | 450 | 74 |
| SystemVerilog (`iris2sv`) | 18 | 445 | 288 |
| Veryl (handwritten) | 30 | 477 | 78 |

SystemVerilog is the shortest by line count. By character count the three are
within five percent of one another.

The difference is formatting. The generated SystemVerilog packs the assignment
to `y` onto one line, and that line is 288 characters long.

Widening to five designs (ALU, decoder, register file, core, asynchronous FIFO)
gives the same shape.

| | Code lines | Non-space characters |
|---|---|---|
| IRIS | 419 | 8,073 |
| SystemVerilog (`iris2sv`) | 268 | 7,799 |

Thirty-six percent fewer lines, three percent fewer characters. **Read as line
counts, this comparison measures formatting habits.**

IRIS and Veryl come out level on both counts.

## Simulation speed

A counter, run three times, median reported.

Speed depends on how the simulation is driven, so the table separates the two
ways. A native binary running a bare loop and a SystemVerilog testbench driven
with `#1` delays are not measuring the same thing.

Driven by a native loop:

| | Cycles | Time | Cycles/s |
|---|---|---|---|
| IRIS compiled (`iris-compile`) | 20M | 0.47 s | 42.6M |
| Verilator (C++ harness calling `eval()`) | 20M | 0.56 s | 35.7M |

The optimisation settings match. Verilator defaults to `OPT_FAST = -Os` while
`iris-compile` builds with `-O3` and link-time optimisation. Without matching
them the comparison measures build settings rather than simulators: left at
`-Os`, Verilator takes 0.72 s and the gap looks larger than it is.

Driven by a SystemVerilog testbench:

| | Cycles | Time | Cycles/s |
|---|---|---|---|
| Verilator (from IRIS via `iris2sv`) | 20M | 2.97 s | 6.73M |
| Verilator (from Veryl via `veryl build`) | 20M | 2.90 s | 6.90M |

For reference, the IRIS interpreter runs 1M cycles in 2.18 s, about 460,000
cycles per second.

**Veryl also has a native simulator.** Verilator (from `veryl build`) is used
here so both languages are measured on the same ground; it does not mean Veryl
can only run on Verilator.

### What each figure is a property of

IRIS and Veryl run at the same speed under Verilator, with the difference inside
the measurement noise.

That is the expected result. Both become SystemVerilog before Verilator sees
anything, so what is being measured is Verilator and the emitter feeding it. A
difference here would say something about the emitters, not about the languages.

The compiled IRIS backend is 1.2 times faster than Verilator. Comparing across
the two tables is meaningless, because the driving method differs.

**The margin depends on the design.** On a design with 32-bit arithmetic it
narrows to 0.52 s against 0.55 s over 20M cycles, a factor of 1.06. The counter
is eight bits wide with a single always block, which suits IRIS; wider
arithmetic closes the gap.

IRIS models four states (0, 1, X and Z) where Verilator by default models two.
IRIS computes in a machine word only while every bit is known and the width is
at most 64; signed operations and expressions that can carry X take the general
path.

## Advantages and disadvantages

### SystemVerilog

Its advantage is the ecosystem. Synthesis, verification and formal tools accept
it directly, UVM and its surrounding assets exist, and engineers who can write
it are not scarce.

Its disadvantages are in the language. About 220 reserved words, implicit type
conversion, and a distinction between blocking and non-blocking assignment that
still runs when it is used wrongly. `begin` and `end` cost more than keystrokes:
they are something to mismatch.

### Veryl

Its advantage is replacing the syntax without giving up the ecosystem. The
output is SystemVerilog, so synthesis and simulation go through today's tools.
There is an official formatter and language server, and the standard library
includes FIFOs and AXI interfaces.

Its disadvantages come from the translation step. Errors from a synthesiser or
simulator point at the generated SystemVerilog, so that is what has to be read.
With no simulator of its own, running anything goes through SystemVerilog.

There is also a problem measured in the translator itself. `veryl translate`
generates Veryl from SystemVerilog, and dropped assignments without reporting an
error even with `--strict`:

| Design | Assignments in SystemVerilog | Surviving translation |
|---|---|---|
| alu | 5 | 1 |
| decoder | 27 | 1 |
| regfile | 4 | 2 |
| riscv_core | 33 | 9 |
| async_fifo | 19 | 17 |

For moving existing SystemVerilog to Veryl, the output cannot be taken on trust.

### IRIS

Its advantage is having a simulator of its own. There are two, an interpreter
and a compiled backend, and the compiled one is faster than Verilator when both
are driven by a native loop. It reaches that while still modelling four states.
Its 58 reserved words are the fewest of the three.

Its disadvantage is the size of the ecosystem. No EDA tool takes IRIS directly,
so everything goes through `iris2sv`.

What that converts is checked against every design in the repository and
against each construct of the grammar:

```
$ tools/conformance/run.sh
pass 123   fail 0
```

`fsm`, `enum`, `struct`, `union`, `interface`, `fn`, `extern mod`, `package`
and testbenches all convert.

A converted testbench is run under Verilator and its report compared against
`iris-sim`:

| Check | `iris-sim` | Converted, under Verilator |
|---|---|---|
| `test_addi` | 0 mismatches | 0 mismatches |
| `test_alu` | 0 mismatches, PASS | 0 mismatches, PASS |
| `test_mem` | 0 mismatches, PASS | 0 mismatches, PASS |
| `test_sys` | 0 mismatches, PASS | 0 mismatches, PASS |

A construct it cannot convert fails with a diagnostic rather than being ignored,
which is the opposite of the `veryl translate` behaviour above.

`sv2iris` cannot carry a testbench's timing back to IRIS. It reads `#5ns` and
`initial`, but IRIS drives both clock and reset from their declarations, so
there is nowhere for them to go. It says so rather than dropping them.

## Regenerating the figures

```bash
cd example/comparison && ./run.sh
```

The equivalence checks run first. Line counts and timings are only measured
after the IRIS and Veryl versions are shown to produce the same output. Timings
vary by a few percent between runs.

The Veryl sources are handwritten. `veryl translate` could have produced them,
but drops assignments as described above.

Measured on:

```
Intel Core i9-12900K, 24 threads
Verilator 5.032
rustc 1.91.1
Veryl 0.20.3
```
