# IRIS、SystemVerilog、Verylの比較

## この資料が扱うもの

ハードウェア記述言語を3つ並べ、構文、記述量、シミュレーション速度を比べる。
どこでどちらが有利かは設計によって変わるので、数字には測った条件を添える。

数字はすべて`example/comparison/run.sh`が作り直す。
引用する前にそれが通ることを確かめてほしい。

比較の対象は次の3つである。

**SystemVerilog**：IEEE 1800として標準化されたハードウェア記述言語。
EDAツールが直接受け付ける。

**Veryl**：SystemVerilogへ変換する言語。
既存のツールをそのまま使いながら、現代的な構文で書ける。

**IRIS**：SystemVerilogへ変換する言語であり、自前のシミュレータも持つ。

VerylとIRISは同じ問題を解いている。
どちらもSystemVerilogの構文を捨てつつ、SystemVerilogの生態系は捨てない。

## 構文

| 機能 | SystemVerilog | Veryl | IRIS |
|------|---------------|-------|------|
| 括弧 | `begin ... end` | `{ ... }` | `{ ... }` |
| 型宣言（組み合わせ） | `wire [7:0] data` | `let data: logic<8>` | `let data: bit[8];` |
| 型宣言（順序） | `reg [7:0] data` | `var data: logic<8>` | `var data: bit[8];` |
| 分岐 | `case ... endcase` | `case { ... }` | `match { ... }` |
| 組み合わせ論理 | `assign` / `always_comb` | `assign` / `always_comb { }` | `let`宣言 / `comb { }` |
| 順序論理 | `always_ff @(posedge clk)` | `always_ff (clk) { }` | `sync(clk.posedge) { }` |
| モジュール | `module ... endmodule` | `module ... { }` | `mod ... { }` |
| 代入演算子 | `=`（ブロッキング）/ `<=`（ノンブロッキング） | `=`（統一） | `=`（統一） |
| 予約語数 | 約220 | 85 | 58 |
| 文法規則数 | 数えていない | 199 | 209 |

予約語数はIRISが仕様2.4節、Verylが`tools/veryl.ebnf`の由来である文法ファイルから数えた。
文法規則数は`tools/iris.ebnf`と`tools/veryl.ebnf`の規則数である。
SystemVerilogの約220は仕様書の記述をそのまま置いた。
SystemVerilogの文法規則数とあわせて、今回は数え直していない。

VerylとIRISは、SystemVerilogから離れる方向がよく似ている。
波括弧を使い、代入演算子を1つにまとめ、予約語を3分の1以下に減らしている。

## 記述量

同じ動作をすることを確かめた設計だけで比べる。
違う回路の行数を並べても意味がない。

IRIS版とVeryl版は手書きで、SystemVerilog版は`iris2sv`が生成したものである。

ALU（RV32Iの10演算）:

| | コード行 | 空白を除く文字数 | 最長行 |
|---|---|---|---|
| IRIS（手書き） | 30 | 450 | 74 |
| SystemVerilog（`iris2sv`生成） | 18 | 445 | 288 |
| Veryl（手書き） | 30 | 477 | 78 |

行数ではSystemVerilogがもっとも短い。
だが文字数では3者が5%以内に収まる。

差は整形である。
生成されたSystemVerilogは`y`への代入を1行に詰めており、その1行が288文字ある。

設計5本（ALU、デコーダ、レジスタファイル、コア、非同期FIFO）に広げても同じ形になる。

| | コード行 | 空白を除く文字数 |
|---|---|---|
| IRIS | 419 | 8,073 |
| SystemVerilog（`iris2sv`生成） | 268 | 7,799 |

行数では36%短いが、文字数では3%しか違わない。
**この比較で行数を見ると、測っているのは整形の癖である。**

IRISとVerylは行数も文字数もほぼ並ぶ。

## シミュレーション速度

カウンタを回した。
各3回実行し、中央値を採っている。

駆動のしかたで速度は変わるので、揃えて並べる。
ネイティブのバイナリが素のループを回すものと、
SystemVerilogのテストベンチを`#1`遅延で駆動するものは、別のものを測っている。

ネイティブのループで駆動したもの:

| 実行系 | 反復 | 時間 | サイクル毎秒 |
|---|---|---|---|
| IRIS コンパイル型（`iris-compile`） | 2000万 | 0.47 s | 約4260万 |
| Verilator（C++ハーネスから`eval()`） | 2000万 | 0.56 s | 約3570万 |

最適化の指定は揃えてある。
Verilatorの既定は`OPT_FAST = -Os`だが、`iris-compile`は`-O3`とリンク時最適化で組む。
揃えなければ、測っているのは実行系ではなくビルド指定である。
既定の`-Os`のままならVerilatorは0.72 sになり、差が実際より大きく見える。

SystemVerilogのテストベンチで駆動したもの:

| 実行系 | 反復 | 時間 | サイクル毎秒 |
|---|---|---|---|
| Verilator（IRISから`iris2sv`で生成） | 2000万 | 2.97 s | 約673万 |
| Verilator（Verylから`veryl build`で生成） | 2000万 | 2.90 s | 約690万 |

参考として、IRISのインタプリタは100万反復で2.18 s、約46万サイクル毎秒である。

### 数字が何の性質なのか

IRISとVerylはVerilator上で同じ速さになる。
差は測定のばらつきの内側に収まっている。

これは当然の結果である。
どちらもVerilatorが見る前にSystemVerilogになっており、
測っているのはVerilatorと、そこへ食わせた変換器の性質だからである。
ここに差が出たとすれば、それは言語の速さではなく変換器の癖を意味する。

IRISのコンパイル型はVerilatorより1.2倍速い。
ただし表の上段と下段を跨いで比べるのは、駆動のしかたが違うので意味がない。

**この差は設計によって変わる。**
32ビットの演算を含む設計では、2000万反復で0.52 s対0.55 s、1.06倍まで縮む。
カウンタは8ビット、alwaysブロック1つで、IRISにとって条件の良い設計である。
幅の広い演算が入ると差は縮む。

IRISが4値（0、1、X、Z）を模擬しているのに対し、Verilatorは既定で2値しか持たない。
IRISは幅64ビット以下でXもZも無い間だけ機械語で計算し、
符号付きの演算やXの現れうる式は一般の経路を通る。

## それぞれの利点と欠点

### SystemVerilog

利点は生態系にある。
合成、検証、形式手法まで、EDAツールが直接受け付ける。
UVMをはじめとする検証資産があり、書ける技術者も多い。

欠点は言語そのものにある。
予約語が約220あり、暗黙の型変換が通り、
ブロッキング代入とノンブロッキング代入の使い分けを間違えても動いてしまう。
`begin`と`end`は打鍵数の問題にとどまらず、対応の取り違えを起こす。

### Veryl

利点は、既存の生態系を捨てずに構文を入れ替えられることにある。
出力はSystemVerilogなので、合成もシミュレーションも今のツールで通る。
公式のフォーマッタと言語サーバがあり、標準ライブラリにはFIFOやAXIインターフェースが入っている。

欠点は変換を挟むことから来る。
合成器やシミュレータが出すエラーは生成されたSystemVerilogを指すので、
そちらを読む場面が残る。
自前のシミュレータを持たないため、実行は常にSystemVerilogを経由する。

もう1つ、変換器の側で確かめた問題がある。
`veryl translate`はSystemVerilogからVerylを生成するが、
`--strict`を付けてもエラーを出さないまま代入を落とした。

| 設計 | SystemVerilogの代入 | 変換後に残った数 |
|---|---|---|
| alu | 5 | 1 |
| decoder | 27 | 1 |
| regfile | 4 | 2 |
| riscv_core | 33 | 9 |
| async_fifo | 19 | 17 |

既存のSystemVerilog資産をVerylへ移す用途では、
生成物をそのまま信じるわけにはいかない。

### IRIS

利点は自前のシミュレータを持つことにある。
インタプリタとコンパイル型の2つがあり、
コンパイル型はネイティブのループで駆動したときVerilatorより速い。
4値を保ったままそれを達成している。
予約語は58語で、3者のうちもっとも少ない。

欠点は生態系の小ささである。
EDAツールが直接受け付けないので、`iris2sv`を経由する。

変換の範囲は、リポジトリにある設計と文法の各構文で確かめている。

```
$ tools/conformance/run.sh
pass 123   fail 0
```

`fsm`、`enum`、`struct`、`union`、`interface`、`fn`、`extern mod`、
`package`、テストベンチのいずれも変換できる。

変換したテストベンチをVerilatorで走らせ、`iris-sim`の報告と突き合わせている。

| 検証 | `iris-sim` | 変換後、Verilator |
|---|---|---|
| `test_addi` | 不一致0 | 不一致0 |
| `test_alu` | 不一致0、PASS | 不一致0、PASS |
| `test_mem` | 不一致0、PASS | 不一致0、PASS |
| `test_sys` | 不一致0、PASS | 不一致0、PASS |

変換できない構文が残っている場合は、黙って無視せず診断を出して失敗する。
上の`veryl translate`と対照的なのはこの点である。

`sv2iris`はテストベンチの時間制御をIRISへ戻せない。
`#5ns`と`initial`は読めるが、
IRISはクロックもリセットも宣言から駆動するので戻す先が無い。
これも診断を出す。

## 数字の作り直し方

この資料の数字は次のコマンドが作り直す。

```bash
cd example/comparison && ./run.sh
```

等価性の確認から先に走る。
IRIS版とVeryl版が同じ出力を返すことを確かめてから、行数と速度を測る。
時間は実行ごとに数%変動する。

Veryl版は手書きである。
`veryl translate`で生成する道もあるが、上に挙げたとおり代入が落ちるため使えない。

計測環境は次のとおりである。

```
Intel Core i9-12900K / 24スレッド
Verilator 5.032
rustc 1.91.1
Veryl 0.20.3
```
